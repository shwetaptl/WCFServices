# WCF Binding Comparison: REST vs SOAP

This solution demonstrates two types of WCF (Windows Communication Foundation) services built on .NET Framework 4.6.1, using the same `GetCustomers` operation to isolate the one thing that makes them behave completely differently: **the binding**.

> WCF is a legacy enterprise communication framework built into the .NET Framework. While modern services use ASP.NET Web API or gRPC, WCF is still widely deployed in financial systems, insurance platforms, and large enterprise backends. 

---

## Solution Structure

```
WCFBindingComparison.sln
├── WCFRestWebService/      — REST service  (webHttpBinding)
├── ConsumingServices/      — REST console client (plain HttpWebRequest)
├── WCFSOAPService/         — SOAP service  (basicHttpBinding)
└── SoapClient/             — SOAP console client (generated proxy)
```

## The Key Difference: Binding Configuration

The single most important WCF concept this repo illustrates is how `binding` in `Web.config` changes everything about how clients interact with the service.

### REST — `webHttpBinding`

**WCFRestWebService/Web.config**
```xml
<endpoint name="RESTEndPoint"
          contract="WCFRestWebService.IRESTServices"
          binding="webHttpBinding"
          address="restPoint"
          behaviorConfiguration="restbehavior" />
```

- Paired with `<webHttp/>` endpoint behavior
- `[WebGet]` on the interface operation maps it to an HTTP GET
- Callable with any HTTP client — browser, curl, Postman
- Returns JSON (`ResponseFormat = WebMessageFormat.Json` set on `[WebGet]`)

```
GET http://localhost:58534/RESTService.svc/restPoint/GetCustomers
```

### SOAP — `basicHttpBinding`

**WCFSOAPService/Web.config**
```xml
<endpoint name="SOAPEndPoint"
          contract="WCFSOAPWebService.ISOAPService"
          binding="basicHttpBinding"
          address="soap" />
```

- No `[WebGet]` — the operation contract is invoked via a SOAP XML envelope
- Not reachable with a plain browser request
- Requires a SOAP client: either a generated proxy (Add Service Reference) or `ChannelFactory<T>`
- Returns XML wrapped in a SOAP envelope

```
POST http://localhost:50095/SOAPService.svc/soap
Content-Type: text/xml
SOAPAction: "http://tempuri.org/ISOAPService/GetCustomers"
```

## Interface Comparison

Both services expose the identical operation contract. Only the attribute on the REST interface differs:

| | REST (WCFRestWebService) | SOAP (WCFSOAPService) |
|---|---|---|
| **Interface attribute** | `[ServiceContract]` | `[ServiceContract]` |
| **Method attribute** | `[OperationContract]` + `[WebGet]` | `[OperationContract]` |
| **Binding** | `webHttpBinding` | `basicHttpBinding` |
| **Transport** | HTTP GET | HTTP POST (SOAP envelope) |
| **Client** | HttpWebRequest / fetch / curl | Generated proxy / ChannelFactory |
| **Response format** | JSON | XML (SOAP envelope) |

## How the Clients Work

### ConsumingServices — REST client

Uses `HttpWebRequest` to call the REST endpoint and prints the raw JSON response. No special framework needed — any HTTP library works.

```csharp
HttpWebRequest request = (HttpWebRequest)WebRequest.Create(
    "http://localhost:58534/RESTService.svc/restPoint/GetCustomers");
HttpWebResponse response = (HttpWebResponse)request.GetResponse();
```

### SoapClient — SOAP client

Uses `SOAPServiceClient`, a proxy class generated by Visual Studio's **Add Service Reference** feature. The proxy handles serializing method calls into SOAP XML envelopes and deserializing the response — the caller works entirely with C# objects.

```csharp
SOAPServiceClient proxy = new SOAPServiceClient();
Customers[] customers = proxy.GetCustomers();
```

The generated proxy lives in `SoapClient/Connected Services/SOAPService/Reference.cs`. The endpoint address is configured in `SoapClient/App.config`, matching the SOAP service's `basicHttpBinding` endpoint.

## Running the Projects

### Prerequisites
- Visual Studio 2017 or later (Windows)
- .NET Framework 4.6.1

### Step 1 — Open the solution
Open `WCFBindingComparison.sln`.

### Step 2 — Run the REST service
Set **WCFRestWebService** as the startup project and press F5. IIS Express starts on port `58534`.

Verify in a browser:
```
http://localhost:58534/RESTService.svc/restPoint/GetCustomers
```
You should see a JSON array of customers.

### Step 3 — Run the REST console client
Set **ConsumingServices** as the startup project and run. The console prints each customer's ID, name, and city.

### Step 4 — Run the SOAP service
Set **WCFSOAPService** as the startup project and press F5. IIS Express starts on port `50095`.

To inspect the WSDL:
```
http://localhost:50095/SOAPService.svc?wsdl
```

### Step 5 — Run the SOAP console client
With the SOAP service running, set **SoapClient** as the startup project and run. The console prints each customer's ID, name, and city.

## Why These Two Patterns Still Matter

Even in 2024, large enterprises maintain WCF SOAP services because:
- SOAP's formal WSDL contract enables strongly-typed client generation in any language
- `basicHttpBinding` is straightforward to expose through a reverse proxy or API gateway
- Existing integrations (EDI, banking systems, insurance platforms) often mandate SOAP

The REST endpoint shows how WCF can also serve lightweight HTTP clients — the `webHttpBinding` + `[WebGet]` pattern was WCF's answer to REST before ASP.NET Web API existed.
